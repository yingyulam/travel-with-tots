Curated venue data (hours, age range, features) queried to ground every plan and replan.

/plan form

Wake-up/bedtime, naps, destination, dining, and preferences a parent fills in before planning.

User in-trip input

/trip page

Situation buttons on the trip page ("Nap happened here", "Need to stay here longer", "Change the theme"...), a typed duration for the two that need one, and a free-text note sent with every replan.

🔵 Agent

AI Agent (OpenRouter)

LLM

A LangGraph tool-calling agent with 4 tools (answer from the knowledge base, read a described day into the planning form, plan a trip, find a nearby place). This is what the site's chat bubble talks to, so answering questions is now one of its tools rather than a separate code path. Its test page watches real bubble traffic instead of having a chat of its own.

🔴 Tools

Plan trips (adjustment)

AI-backed

src/components/plan_trip.py: a rule-based draft, then PlanningAgent.adjust_plan() smooths it -- a genuine judgment call, not something rules alone can decide. Used by both /plan and the AI Agent's tool.

Try it

Replan a trip on-the-go (adjustment)

AI-backed

src/components/replan_trip.py: same pattern as Plan trips, for a mid-trip situation. Used by the /trip page's replan flow.

Try it

Venue proposer

AI-backed

src/workflows/propose_venues.py: searches the web for real places a parent could take a toddler and writes a small batch of candidates with the URL each claim came from. It proposes no amenity and no opening hours, because a search result cannot establish them, and it never writes a venue itself. A person approves candidates in the review queue, and rejections are remembered so a place you turn down is not offered again.

Try it

Form extractor

AI-backed

src/components/extract_form.py: reads a parent's description of their day into the planning form, so they can say it in their own words instead of filling in boxes. The model only proposes; every value goes through the same read_form the /plan route uses, so the clamps and caps are enforced by the real validator. Anything the description does not mention is reported as a default rather than guessed at.

Try it

Find nearby stops

deterministic

src/components/find_nearby.py: ranks venues by real straight-line distance from your location, then matches your need (restaurant, nursing room, quiet spot...) using the same interactions.find_nearby() the trip page already used. Venues without coordinates fall back to same-neighbourhood-first. Falls back to a live web search when the venue table has nothing. Intentionally not AI, since there's no judgment call to make.

Try it

Look up saved plans

deterministic

The dashboard and saved-trip pages read straight from the database -- not something the AI agent invokes itself.

Web Search

API-backed

Live results from the Tavily Search API (src/components/search_web.py). Find nearby stops escalates to it when the curated venue table has nothing for a need, normalising its results into the same shape a venue has so a caller renders one list either way. The standalone page below stays for trying queries directly.

Try it

Place Search

API-backed

src/components/place_search.py: finds a place by name via Google Places, so Log a Place can offer candidates to pick from instead of asking a parent to describe a location twice. Separate from Geocode on purpose: that one turns an address into coordinates, this one answers "which place did you mean", and geocoding a business name tends to return a street. Server-side like every other key, and the key travels in a header rather than a URL, so a logged request can't carry it.

Try it

Google Map handoff

API-backed

src/components/geocode.py: turns a typed address into coordinates via the Google Geocoding API. It has no page of its own, since it only ever supports another component: it is the "set a location by hand" path on Find Nearby. Sharing a location needs no key, because venues carry their own coordinates. Travel-time routing and the accommodation field are still to come.
