🟡 Data Connectors

Venues DB

SQLite, the runtime source of truth

One venues table grounding every plan and replan: name, type, setting (indoor/outdoor/both), neighbourhood, coordinates, and one open/close pair plus a free-text hours note for what a pair cannot hold. Three sources write to it, and the source field records which: the curated seed, the City's open data, and places a parent logged. Amenities are deliberately not columns here -- they live in Parent reports, so a claim always carries who made it and when.

User initial trip input

/plan form

Wake-up/bedtime, naps, destination, dining, and preferences a parent fills in before planning.

User in-trip input

/trip page

Situation buttons on the trip page ("Nap happened here", "Need to stay here longer", "Do something else"...), a typed duration for the two that need one, and a free-text note sent with every replan.

City of Vancouver Open Data

API-backedno review

src/clients/opendata.py talks to the City, src/importers.py decides what a venue is. Parks and community centres are imported straight into the venues table with no review step: the City is more reliable about its own parks than any reviewer we could put in front of them. Public washrooms are read as an attribute of a park, never as a venue of their own. An import fills blanks and never overwrites a value, and it matches an existing curated venue by name so the curator's ranked row is upgraded in place rather than duplicated. Keyless and openly licensed. Run from scripts/import_open_data.py, which is a dry run unless told otherwise, so it has no page here.

OpenStreetMap (Overpass)

API-backed

src/clients/osm.py, the outside opinion on opening hours. Two callers, and neither acts on what it finds: scripts/verify_hours.py compares our stored hours against OSM and flags disagreements for a person, since hours are entered once at review and nothing else writes them; and the Venue proposer prefills a candidate's hours before review, so a reviewer confirms instead of types. It also carries the venue's own website, which is where Official site looks first. Chosen over a commercial API because it is openly licensed, so a result can be stored and shown with attribution. Overpass rate-limits hard, so names are batched into one query per run and this is not called from a page.

Nominatim

API-backed

src/clients/nominatim.py: a place name to coordinates, keyless and ODbL. Used by the Venue proposer only, and nothing a parent touches, which is why it has no page. It replaced Google Places on that path: Places terms allow keeping a place id but restrict retaining returned content, and everything the proposer writes lands in a CSV tracked in git. Paced at one request a second, and a bare-name hit is accepted only when the result is really in British Columbia, because searching for "Vancouver" reaches Washington too.

Parent reports

no review

The venue_reports table: what a parent found when they were actually there (washroom, nursing room, high chair, step-free access), written from the trip page and never gated on review. Every claim carries an author and a date, so "nobody has said" reads differently from "somebody looked and there was none", and the newest report wins a disagreement. This is why amenities are not venue columns.

🔵 Agent

AI Agent (OpenRouter)

LLM

A LangGraph tool-calling agent with 4 tools (answer from the knowledge base, read a described day into the planning form, plan a trip, find a nearby place). This is what the site's chat bubble talks to, so answering questions is now one of its tools rather than a separate code path. Its test page watches real bubble traffic instead of having a chat of its own.

Memory

deterministic

src/memory.py: recall() turns a parent id into what the app already knows -- a child's age, the routine from the last day they saved -- so the chat can reuse it instead of asking again. Read only, and no new source of truth: an age is recomputed from a date of birth on every call, and a draft is not memory. Nothing is learned or inferred; nap_notes and extra_notes are still per-trip form fields.

Soul

not implemented yet

No unified persona/values layer yet -- today there are separate, editable system prompt files per feature (see Settings).

Opening-hours check

deterministic

src/components/validate_hours.py: the last thing a plan passes before a parent sees it. Checks every stop against that venue's one open/close pair for the trip date, then swaps a closed venue for an open one or leaves the slot free. A statutory holiday is the one date that changes the answer: somewhere with no door keeps its pair, everything else reads as unknown, because a default pair says nothing about Christmas. Deterministic on purpose: comparing a time to stored hours is arithmetic. A venue whose hours we do not know is treated as closed, never as open.

Venue proposer

AI-backed

src/workflows/propose_venues.py: searches the web for the places the City does not own -- museums, aquariums, attractions -- and writes a small batch of candidates with the URL each claim came from. It never writes a venue itself. Coordinates come from Nominatim and hours from OpenStreetMap, never from the model, and only where OSM reads as one plain pair; anything richer is left for the reviewer. It proposes no amenity, because a search result cannot establish one. A person approves candidates in the review queue, which is the only path that turns a candidate into a venue, and rejections are remembered so a place you turn down is not offered again.

Try it

Form extractor

AI-backed

src/components/extract_form.py: reads a parent's description of their day into the planning form, so they can say it in their own words instead of filling in boxes. The model only proposes; every value goes through the same read_form the /plan route uses, so the clamps and caps are enforced by the real validator. Anything the description does not mention is reported as a default rather than guessed at.

Try it

Find nearby stops

deterministic

src/components/find_nearby.py: ranks venues by real straight-line distance from your location, then matches your need (restaurant, nursing room, quiet spot...) using the same interactions.find_nearby() the trip page already used. Venues without coordinates fall back to same-neighbourhood-first. Falls back to a live web search when the venue table has nothing. Intentionally not AI, since there's no judgment call to make.

Web Search

API-backed

Live results from the Tavily Search API (src/components/search_web.py). Find nearby stops escalates to it when the curated venue table has nothing for a need, normalising its results into the same shape a venue has so a caller renders one list either way. The standalone page below stays for trying queries directly.

Place Search

API-backed

src/components/place_search.py: finds a place by name via Google Places, so Log a Place can offer candidates to pick from instead of asking a parent to describe a location twice. Separate from Geocode on purpose: that one turns an address into coordinates, this one answers "which place did you mean", and geocoding a business name tends to return a street. It backs the parent-facing lookups only -- Log a Place, /place-search, Find Nearby -- since the proposal path moved to Nominatim, whose results it is allowed to store. Server-side like every other key, and the key travels in a header rather than a URL, so a logged request can't carry it.

Try it

Google Map handoff

API-backed

src/components/geocode.py: turns a typed address into coordinates via the Google Geocoding API. It has no page of its own, since it only ever supports another component: it is the "set a location by hand" path on Find Nearby. Sharing a location needs no key, because venues carry their own coordinates. The accommodation picker on the planning form needs none either: it is Leaflet with OpenStreetMap tiles, because every Google embed puts the key in the browser. Travel-time routing is still to come, and deliberately so.
